# bin-file-fmt (binpazer) -- developer notes

The binpazer block-container format (SPEC.md, the interop contract) with three
implementations that must stay in lockstep. README.md is the user story; this
file is for working on the code.

## The invariant: three implementations, byte-identical output

C, C++, and Go all write **byte-identical** files. The canonical fixture is
`go/testdata/sample.binpazer`, generated by the C reference (`c/gen.c`); the Go
tests compare against it, and CI regenerates and `cmp`s it on every push. Check
locally:

```sh
cc -std=c11 -O2 c/binpazer.c c/gen.c -o /tmp/binpazer_gen
/tmp/binpazer_gen /tmp/sample.binpazer
cmp /tmp/sample.binpazer go/testdata/sample.binpazer
```

Any writer-side change that alters output bytes breaks the other two
implementations and the fixture. Either keep bytes identical, or change all
three writers *and* regenerate the fixture in the same commit -- never one
without the others.

## Build & test

```sh
make -C c test               # C11 round-trip tests
make -C cpp test             # C++17 round-trip tests
cd go && go-toolchain        # tidy + vet + tests + coverage gate + go/build/binpazer
```

ASan+UBSan variants (exactly what CI runs):

```sh
cc  -std=c11   -Wall -Wextra -O1 -fsanitize=address,undefined -fno-sanitize-recover=all c/binpazer.c c/test.c -o /tmp/test_c_san && /tmp/test_c_san
c++ -std=c++17 -Wall -Wextra -O1 -fsanitize=address,undefined -fno-sanitize-recover=all -Ic cpp/test.cpp c/binpazer.c -o /tmp/test_cpp_san && /tmp/test_cpp_san
```

Go rules:

- **Never run bare `go` commands** -- always `go-toolchain` (no arguments) from
  `go/`. It enforces >=80% coverage and a per-file line budget (warning at 500
  lines, **hard fail at 750** -- `reader.go` sits near 600, so split before
  adding bulk). Accept whatever it auto-rewrites (formatting, imports, go.mod)
  and commit those changes.
- Do not pipe go-toolchain's output (`| tail` etc.) -- it refuses to run.
- **Exception:** `go-toolchain` cannot drive fuzzing engines; a real fuzz
  session uses the Go binary the toolchain provisioned (e.g.
  `/usr/local/go/bin/go`):

  ```sh
  cd go && /usr/local/go/bin/go test -fuzz=FuzzReader -fuzztime=60s .
  ```

CI (`.github/workflows/ci.yml`): a `go` job (`wow-look-at-my/go-toolchain@v1`)
and a `c-cpp` job (make tests, both ASan builds, the fixture `cmp` above),
plus a `publish` job gated on both that ships the CLI matrix binaries to
https://pazer.build as project `bin-file-fmt/binpazer`. The project name is
repo-derived because buildhost scopes a repo's OIDC token to the repo's own
namespace (`bin-file-fmt` and `bin-file-fmt/<...>`); a `project: binpazer`
override gets a 404 -- do not "fix" the name. `publish` gets the binaries from
go-toolchain's `go-build-go` cache hand-off (org CI has no GHA artifacts) and
needs `deployments: write` -- buildhost-publish registers a GitHub Deployment
and fails without it. Nothing merges red.

## Layout

`SPEC.md` is the format spec; `c/` is the allocation-free C11 reference
(`binpazer.h`/`binpazer.c`, tests in `test.c`, fixture generator `gen.c`);
`cpp/` is a header-only C++17 wrapper over the C core (`binpazer.hpp`); `go/`
is a pure-Go library at the package root plus the cobra CLI in
`go/cmd/binpazer/` (one command per file). `go/testdata/sample.binpazer` is
the shared 280-byte fixture.

## IO-injection seam (deliberate -- do not add mmap)

The libraries do **no file IO and no mmap**; the caller injects IO. C/C++ take
`read`/`write` (+ optional `seek`) callbacks; Go takes `io.Reader`/`io.Writer`
and *sniffs* `io.Seeker` on both sides -- the Reader uses it for the input-size
probe, seek-based skipping, and footer/Block Index jumps; the Writer uses it to
back-patch `file_length` (non-seekable output keeps the streaming sentinel).
Everything degrades gracefully without a seeker: sequential walk, read-through
skip, `NewReaderLimited` caps. Performance fixes go through the captured
seeker, not through new IO paths.

## Go package architecture

- `binpazer.go` -- shared constants/types (flags, predefined type ids/GUIDs,
  `ioBufSize` = 64 KiB shared by reader/writer/streaming).
- `reader.go` -- header/BTT parse, block walk, footer probe, `Find`/`At`
  index jumps. **`claim()` is the allocation gate**: every untrusted
  length/count is checked against the remaining input size (seekable) or the
  configured cap *before* any `make`. New parsing code must route through it.
- `errors.go` -- typed sentinels (`ErrBadMagic`, `ErrCRCMismatch`,
  `ErrTruncated`, `ErrCapacityExceeded`), matched with `errors.Is`. Keep new
  failure modes typed; callers (validate) dispatch on them.
- `NewReaderLimited(r, maxAlloc)` -- reader for non-seekable inputs with an
  explicit per-field cap (`DefaultMaxAlloc` = 1 GiB; `maxAlloc<=0` selects it).
  Seekable inputs ignore the cap and use the real size, learned in `NewReader`.
- `payload.go` -- streaming: `WritePayloadTo` (64 KiB chunks, incremental CRC)
  and `PayloadReader` (bounded reader, `SkipPayload` realigns afterwards). The
  CLI never buffers whole payloads; keep it that way (RSS stays ~3 MB on 1 GiB
  files).
- `writer.go` -- buffered writer + index/footer emission; `group.go` --
  `ParseGroupPayload` for nested blocks; `guid.go` -- GUID parse/format.
- All reads go through a `bufio.Reader`, so the raw input position can be
  ahead of the logical offset: reposition **only** via `seekTo(abs)` (never a
  raw relative seek).

## CLI conventions (go/cmd/binpazer)

- cobra; one top-level command per file; each registers itself in its own
  `init()`. Never centralize registration.
- `-` means stdin/stdout for positional file args and `--out`/`-o` only.
- **cobra flag values are sticky across `Execute()` calls** -- tests must run
  commands through `execute`/`executeIO` in `helpers_test.go`, which reset flag
  state between invocations. A new test that calls `rootCmd.Execute()` directly
  will pass alone and corrupt the suite.

## Fuzzing

`go/fuzz_test.go` `FuzzReader` walks blocks, streams payloads, and exercises
`Find`/`At` on arbitrary bytes. Its `f.Add` seeds (canonical sample, OOM-repro
claims, corrupt CRC, truncated prefixes) run as plain tests in CI; real fuzz
sessions use the command in Build & test. Add a seed for every new
crafted-input bug you fix.

## validate <-> SPEC

`binpazer validate` implements SPEC.md's "Validation" section: the rule ids in
`go/cmd/binpazer/validate_checks.go` (`allRules`) map one-to-one onto that
checklist plus its implied checks (CRC trailers, footer/index consistency,
structural parseability). If the checklist changes, update the rules and
`validate_rules_test.go` (one corruption test per rule) together.

Decision to preserve: the `unknown_type_id` rule **exempts predefined ids
65530-65534** (SPEC.md notes the exemption). The writer emits the Block Index
(65533) without a BTT entry and writer bytes are frozen; a strict reading
would flag every indexed file. Teaching the writer to add the entry instead
would change output bytes in all three implementations plus the fixture.

## Compression (1.1)

Block flag bit 2 is `compressed`: the stored payload is a **Compression
Envelope** (codec id + reserved + `uncompressed_length`, plus a 16-byte GUID
for the `65535` escape), so codec identity lives in the format, not in a
boolean. The earlier `compressed` flag was removed for exactly that reason;
this is the codec-identifying mechanism SPEC.md said would replace it.

Invariants worth knowing before touching it:

- **Go implements every codec the registry names** -- `stored`, `deflate`,
  `zstd` (klauspost/compress), `lz4` (pierrec/lz4). A caller should not have to
  supply a codec the format itself names; that only guarantees files this
  library writes are files it cannot read.
  `RegisterCodec`/`RegisterCodecGUID` are for codecs OUTSIDE the registry (the
  GUID escape) or to override a built-in.
- **C and C++ carry no codec**, by contract: they do no allocation and no IO,
  so they write and parse the envelope around bytes the CALLER encoded
  (`binpazer_writer_block_compressed`, `binpazer_compression_parse`). Do not add
  a codec dependency to either -- the asymmetry is deliberate, and `stored`
  keeps a well-formed envelope writable from them with nothing linked in.
- `stored` (id 1) exists so every implementation can produce a well-formed
  envelope with no dependency; it is what the cross-impl fixture uses.
- **`length` still counts STORED bytes**, so walking, skipping, `large_mode`,
  the Block Index and CRCs are untouched, and a 1.0 reader traverses a 1.1 file
  correctly. `has_crc` covers the stored bytes, before any codec runs.
- **A file with no compressed block is byte-identical to a 1.0 file** and still
  declares 1.0. `version_minor` is raised to 1 only when a compressed block is
  written, back-patched by `writer_end`/`End` -- which is why a compressed
  block needs a seekable writer (Go's `NewWriterVersion` declares it up front
  for streaming callers; C returns `BINPAZER_ERR_NOSEEK`).
- `go/testdata/sample-compressed.binpazer` is the second cross-impl fixture,
  generated by `gen <out> <compressed-out>` and `cmp`'d in CI like the first.
- The CLI carries compression through `codec` in the pack/unpack manifest --
  never a `compressed` flag name -- so a manifest cannot claim compression
  without naming what produced the bytes. `unpack` writes DECODED payloads.
