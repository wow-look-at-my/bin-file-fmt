# bin-file-fmt (binpazer) -- developer notes

The binpazer block-container format (SPEC.md, the interop contract) with multiple implementations that must stay in lockstep. README.md is the user story. This file is for working on the code.

## The invariant: every implementation writes byte-identical output

C, C++, Go, TypeScript and Python all write **byte-identical** files. The canonical fixture is `go/testdata/sample.binpazer`, generated by the C reference (`c/gen.c`). The Go tests and the TypeScript tests (`ts/src/fixtures.test.ts`) compare against it, and CI regenerates and `cmp`s it on every push. Check locally:

```sh
cc -std=c11 -O2 c/binpazer.c c/gen.c -o /tmp/binpazer_gen
/tmp/binpazer_gen /tmp/sample.binpazer
cmp /tmp/sample.binpazer go/testdata/sample.binpazer
```

Any writer-side change that alters output bytes breaks the other implementations and the fixture. Either keep bytes same, or change all writers *and* regenerate the fixture in the same commit -- never one without the others.

## Build & test

```sh
make -C c test               # C11 round-trip tests (core, then codecs)
make -C cpp test             # C++17 round-trip tests (core, then codecs)
cd go && go-toolchain        # tidy + vet + tests + coverage gate + go/build/binpazer
cd ts && ts0 test            # type-check + TypeScript tests (ts0 build emits ts/dist)
make -C py test              # builds the native CRC library, then the Python tests (unittest)
```

The codec targets need `zlib1g-dev libzstd-dev liblz4-dev`. The TypeScript suite needs them too, plus the `lz4` tool: it compiles `c/interop.c` and checks its LZ4 encoder against the reference decoder. `ts0` comes from `https://apt.pazer.build/ts0` and needs Node 22.18 or newer. The TypeScript package has no npm dependency and no `node_modules`.

ASan+UBSan variants (exactly what CI runs):

```sh
cc  -std=c11   -Wall -Wextra -O1 -fsanitize=address,undefined -fno-sanitize-recover=all c/binpazer.c c/test.c -o /tmp/test_c_san && /tmp/test_c_san
c++ -std=c++17 -Wall -Wextra -O1 -fsanitize=address,undefined -fno-sanitize-recover=all -Ic cpp/test.cpp c/binpazer.c -o /tmp/test_cpp_san && /tmp/test_cpp_san
```

Go rules:

- **Never run bare `go` commands** -- always `go-toolchain` (no arguments) from `go/`. It enforces >=80% coverage and a per-file line budget (warning at many lines, **hard fail at 750** -- split a file before it gets there). Accept whatever it auto-rewrites (formatting, imports, go.mod) and commit those changes.
- Do not pipe go-toolchain's output (`| tail` etc.) -- it refuses to run.
- **Exception:** `go-toolchain` cannot drive fuzzing engines. A real fuzz session uses the Go binary the toolchain provisioned (e.g. `/usr/local/go/bin/go`):

  ```sh
  cd go && /usr/local/go/bin/go test -fuzz=FuzzReader -fuzztime=60s .
  ```

CI (`.github/workflows/ci.yml`) has a `go` job (`wow-look-at-my/go-toolchain@master`, then the C<->Go codec interop check, which needs the CLI that job just built). It has a `c-cpp` job (make tests, both ASan builds, the fixture `cmp` above). It also has a `publish` job gated on both that ships the CLI matrix binaries to https://pazer.build as project `bin-file-fmt/binpazer`. The project name is repo-derived because buildhost scopes a repo's OIDC token to the repo's own namespace (`bin-file-fmt` and `bin-file-fmt/<...>`). A `project: binpazer` override gets a 404 -- do not "fix" the name. `publish` gets the binaries from go-toolchain's `go-build-go` cache hand-off (org CI has no GHA artifacts) and needs `deployments: write` -- buildhost-publish registers a GitHub Deployment and fails without it.

The `ts` job runs `wow-look-at-my/ts0@master` on `ts/` (type-check, the suite, the build). The `py` job runs `make -C py test`. The `bench` job needs `go`: it builds the C and C++ bench programs, takes the CLI from the same cache hand-off, and runs `node bench/run.ts --quick --profile`. That run fails when implementations disagree. It is the live interop check across all of them. `publish` waits for every job.

Nothing merges red.

## Layout

`SPEC.md` is the format spec. `c/` is the allocation-free C11 reference (`binpazer.h`/`binpazer.c`, tests in `test.c` and `test_append.c`, fixture generator `gen.c`) plus the codec layer (`binpazer_codec.h`/`.c`, tests in `test_codec.c`) and the cross-impl harness `interop.c`. `cpp/` is a header-only C++17 wrapper over both. `go/` is a pure-Go library at the package root -- `compress.go` for the envelope and codecs, `codecbuf.go` for the caller-buffer layer. Plus the cobra CLI in `go/cmd/binpazer/` (one command per file). `go/testdata/sample.binpazer` is the shared 280-byte fixture.

`ts/` is the TypeScript package (`src/`, with its `*.test.ts` beside the sources and `bench/bench.ts` as its bench program). `py/` is the Python package. `bench/` is the cross-implementation benchmark: one bench program per implementation, the driver `run.ts`, and the committed `RESULTS.md`.

## Parity across implementations

Anything one implementation can express, every other one must -- a file none of the others can read is the bug this rule exists to prevent. Whole-surface pairs to keep in step when adding to any of them:

| Capability | Go | C / C++ | TypeScript |
|---|---|---|---|
| every registry codec | built in | `binpazer_codec.c` (link it) | `codec.ts` (import `index.ts`) |
| caller-buffer codec API | `CompressInto`/`DecompressInto`/`CompressBound` | `binpazer_compress`/`_decompress`/`_compress_bound` | `compressInto`/`decompressInto`/`compressBound` |
| compress a block from logical bytes | `CompressedBlock` | `binpazer_writer_block_compress` / `Writer::compress_block` | `compressBlock` |
| read a block, decoding it | `ReadDecompressedPayload` | `binpazer_reader_read_payload_decompressed` | `readPayloadDecompressed` |
| stream a payload bigger than memory | `PayloadReader`/`WritePayloadTo` | `binpazer_reader_stream_payload` / `Reader::stream_payload` | `Reader.streamPayload` |
| nested blocks in a Group | `ParseGroupPayload` | `binpazer_group_parse` / `parse_group` | `parseGroup` |
| declare 1.1 up front (streaming writer) | `NewWriterVersion` | `binpazer_writer_begin_version` / `Writer(..., version_minor)` | `new Writer(..., { versionMinor })` |
| GUID <-> canonical text | `ParseGUID` / `GUID.String` | `binpazer_guid_parse` / `_format` / `to_string` | `parseGuid` / `formatGuid` |
| is a codec available? | `LookupCodec` / `LookupCodecGUID` | `binpazer_codec_lookup` | `lookupCodec` |
| start an appendable file | `NewAppendWriter` | `binpazer_writer_begin_append` / `Writer(binpazer::appendable, ...)` | `new Writer(..., { appendable: true })` |
| read only committed blocks | `NextCommitted` | `binpazer_reader_next_committed` / `Reader::next_committed` | `Reader.nextCommitted` |
| continue an open appendable file | `ResumeAppendWriter` | `binpazer_writer_resume` / `Writer(binpazer::resume, ...)` | `resumeAppendWriter` |

Python has every row, under the snake_case form of the TypeScript name.

Known and deliberate differences: Go's `NewReaderLimited` allocation cap has no C counterpart because C allocates nothing -- every buffer is the caller's. The cap is theirs already. The CLI is Go-only. `c/interop.c` is a test harness, not a tool. TypeScript's `nextCommitted` returns `"pending"` for both in-progress and torn bytes, and `Reader.torn` tells them apart. It needs a source with `seek` and `size`, and it asks `size()` again on every call.

This is because that is how it learns that the file grew. TypeScript holds every `u64` as a JS number, so an offset or a length above `Number.MAX_SAFE_INTEGER` is a `range` error there.

Its deflate and zstd go through `node:zlib`, which allocates the codec output before the copy into the caller's buffer.

## CRC-32C in the C core

`binpazer_crc32c` asks the running CPU and takes the fastest path it has, with GCC or Clang:

| Tier | Path | Needs |
|---|---|---|
| 0 | slicing tables | nothing: every other target and compiler |
| 1 | one stream through the CRC instruction | x86-64 SSE4.2, or arm64 CRC |
| 2 | three streams, joined with a carry-less multiply | x86-64 PCLMULQDQ, or arm64 PMULL |
| 3 | carry-less folding across several vector accumulators | x86-64 AVX-512F, AVX-512VL and VPCLMULQDQ, or arm64 PMULL |

The default stops at tier 2 on arm64 Linux and goes to tier 3 everywhere else, because the measurements below differ by CPU.

- `-DBINPAZER_CRC_TIER=<n>` caps the tier at build time. `make -C c test` runs the core tests at every tier, so no path goes untested on a CPU that has a better one.
- `c/tools/crc32c_constants.mjs` derives the multiply constants and checks each one. `c/tools/crc_speed.c` prints the throughput per buffer size.
- The wide path must clear the upper vector state before it calls the SSE-encoded code. Without `_mm256_zeroupper()` a 4 KiB input ran a few times slower.
- C++ and Python call the same function, so they get every tier.

Measured with `c/tools/crc_speed.c` on a Xeon with AVX-512 and VPCLMULQDQ, in GiB/s. The XXH3 column is xxHash 0.8.2 built with `-O3 -march=native`, for scale: a different hash is not a faster one here.

| Buffer | Tier 0 | Tier 1 | Tier 2 | Tier 3 | XXH3 |
|---|---:|---:|---:|---:|---:|
| 1 KiB | 1.92 | 7.03 | 13.12 | 23.91 | 26.44 |
| 4 KiB | 1.95 | 7.15 | 16.42 | 62.19 | 39.51 |
| 64 KiB | 1.93 | 7.34 | 21.75 | 63.29 | 51.28 |
| 1 MiB | 1.94 | 7.30 | 21.77 | 64.11 | 50.47 |
| 8 MiB | 1.92 | 7.04 | 19.09 | 25.17 | 24.91 |

- The 8 MiB row is the memory, not the hash: XXH3 stops at the same rate.
- Tier keeps multiple accumulators. Eight measured no faster on this CPU, so the multiplier is the limit.

The `c-arm64` CI job runs `make -C c test-core` and `make -C c speed` on real arm64 CPUs and prints the throughput to its summary. From its first runs, 1 MiB buffer, in GiB/s:

| CPU | Tier 0 | Tier 1 | Tier 2 | Fold, 8 lanes | Fold, 12 lanes | Fold, 16 lanes |
|---|---:|---:|---:|---:|---:|---:|
| arm64 Linux runner, first run | 2.28 | 13.88 | 23.49 | 18.04 | 17.72 | 19.42 |
| arm64 Linux runner, second run | 2.28 | 13.82 | 23.10 | 18.07 | 17.68 | 19.19 |
| Apple silicon runner, first run | 1.19 | 5.74 | 16.31 | 42.01 | 54.84 | 56.14 |
| Apple silicon runner, second run | 1.34 | 4.95 | 16.79 | 40.49 | 53.35 | 61.02 |

- On the Linux core the streams of tier 2 beat every fold. So the streams are the default there. On Apple silicon the fold wins, and it gains with every lane count the job times. So `CRC_NEON_LANES` is at the highest of them.
- Both runners are shared virtual machines, and the Apple numbers moved by a third between buffer sizes. Read them as an order.
- Change a default only with a new run of that job as the evidence.

## IO-injection seam (deliberate -- do not add mmap)

The libraries do **no file IO and no mmap**. The caller injects IO. C/C++ take `read`/`write` (+ optional `seek`) callbacks. Go takes `io.Reader`/`io.Writer` and *sniffs* `io.Seeker` on both sides. The Reader uses it for the input-size probe, seek-based skipping, and footer/Block Index jumps. The Writer uses it to back-patch `file_length` (non-seekable output keeps the streaming sentinel).

Everything degrades gracefully without a seeker: sequential walk, read-through skip, `NewReaderLimited` caps. Performance fixes go through the captured seeker, not through new IO paths.

## Go package architecture

- `binpazer.go` -- shared constants/types (flags, predefined type ids/GUIDs, `ioBufSize` = 64 KiB shared by reader/writer/streaming).
- `reader.go` -- header/BTT parse, block walk, footer probe, `Find`/`At` index jumps. **`claim()` is the allocation gate**: every untrusted length/count is checked against the remaining input size (seekable) or the configured cap *before* any `make`. New parsing code must route through it.
- `errors.go` -- typed sentinels, matched with `errors.Is`. Keep new failure modes typed, callers (validate) dispatch on them.
- `NewReaderLimited(r, maxAlloc)` -- reader for non-seekable inputs with an explicit per-field cap (`DefaultMaxAlloc` = 1 GiB. `maxAlloc<=0` selects it). Seekable inputs ignore the cap and use the real size, learned in `NewReader`.
- `payload.go` -- streaming: `WritePayloadTo` (64 KiB chunks, incremental CRC) and `PayloadReader` (bounded reader, `SkipPayload` realigns afterwards). The CLI never buffers whole payloads. Keep it that way (RSS stays ~3 MB on files).
- `container.go` -- convenience layer for the shape most files take (content blocks + a directory naming their offsets + index/footer). Pure composition of the primitives -- it adds no format feature, so files it writes are ordinary binpazer files C and C++ already read. It is exempt from the parity table for that reason. New sugar belongs here, not in reader.go/writer.go.
- `append.go`, `follow.go` -- appendable files: the append writer and resume, and `NextCommitted`. `locate.go` -- `Find`/`At`.
- `writer.go` -- buffered writer + index/footer emission, `group.go` -- `ParseGroupPayload` for nested blocks (`binpazer_group_parse` in C, `binpazer::parse_group` in C++ -- same tolerance for a damaged group: the intact prefix comes back with the error). This also covers `guid.go` -- GUID parse/format.
- All reads go through a `bufio.Reader`, so the raw input position can be ahead of the logical offset: reposition **only** via `seekTo(abs)` (never a raw relative seek). `seekTo` also keeps the first read after it small (`readahead.go`), so a lookup by offset does not refill the whole buffer for one small block. The TypeScript reader does the same in `fill()`.

## Python package (py/)

- `py/binpazer/` is the package, `py/tests/` is its `unittest` suite, and `py/bench/bench.py` is its bench program. Python 3.10 or newer, no package from PyPI, tabs for indentation.
- IO is a binary file object: `read` for the reader, `write` for the writer. Both sniff `seekable()`, as Go sniffs `io.Seeker`. The reader keeps no buffer of its own. Wrap a raw input in `io.BufferedReader`.
- `Reader._claim()` is the allocation gate, as in Go and TypeScript. New parsing code goes through it. `tests/test_hardening.py` ports the Go hardening cases.
- Every `u64` is a Python int. So no offset read from a file gives a `range` error, and a footer offset past the input is `truncated`.
- CRC-32C is the C reference's `binpazer_crc32c`, called through `ctypes` (`_native.py`). `make -C py native` builds its shared library from `c/binpazer.c`, and an import builds it when it is absent or stale. Never add a pure-Python CRC, not even as a fallback. A missing compiler fails the import and names the build command.
- `codec.py` binds the system libzstd and liblz4 with `ctypes`, at the first use of the codec. A missing library is `codec_unavailable`, not a silent `stored`.
- `tests/test_append.py` holds "at every prefix a follower sees exactly the whole blocks", the safety proof for this reader.

## TypeScript package (ts/)

- `core.ts` re-exports the dependency-free core. None of them imports `node:*`, and `core-deps.test.ts` fails when one does. `index.ts` adds `codec.ts`, the only file that imports `node:zlib`.
- IO is synchronous and injected: a `Source` (`read`, optional `seek` and `size`) and a `Sink` (`write`, optional `seek`). The library opens no file.
- **A sink may keep the chunks it gets**, as a Node or Web stream does. So the writer never rewrites bytes it passed to a sink: `flush()` hands over a slice and keeps filling the rest of the same buffer. A full buffer is replaced, not reused. A payload larger than the buffer is the caller's array. The writer passes a copy unless the sink sets `borrowsChunks`. Reusing the buffer again corrupts every stream output in silence. The stream sinks are in `stream.ts`, and `stream.test.ts` runs them against real streams.
- `Reader.claim()` is the allocation gate, as in Go. It checks every untrusted length against the input size, or against `maxAlloc` when the size is unknown, before anything is allocated. New parsing code goes through it.
- The reader accepts and rejects the same inputs as the Go reader. `hardening.test.ts` ports the Go hardening cases. Keep it so when either side changes.
- Erasable syntax only (no `enum`, no parameter properties), relative imports carry `.ts`, and `ts0` rejects `any`. Node then runs the sources directly.
- `writer.ts` writes appendable files too (`new Writer(..., { appendable: true })`, `resumeAppendWriter`), and `Reader.nextCommitted` follows them. `append.test.ts` pins both against the shared fixtures.

## Benchmarks (bench/)

`bench/README.md` has the workloads and the commands. Every bench program obeys one command-line contract and prints one result line. The driver fails when implementations print different lines or write different bytes where the format requires equal bytes. `bench/RESULTS.md` and `bench/results.json` come from a full run on one machine. Regenerate them with `node bench/run.ts --profile` after a change that can move CPU time or memory. A bench program measures the library, so keep its own work per byte at zero: sample a payload, and never scan it.

## CLI conventions (go/cmd/binpazer)

- cobra, one top-level command per file. Each registers itself in its own `init()`. Never centralize registration.
- `-` means stdin/stdout for positional file args and `--out`/`-o` only.
- **cobra flag values are sticky across `Execute()` calls** -- tests must run commands through `execute`/`executeIO` in `helpers_test.go`, which reset flag state between invocations. A new test that calls `rootCmd.Execute()` directly will pass alone and corrupt the suite.

## Fuzzing

`go/fuzz_test.go` `FuzzReader` walks blocks, streams payloads, and exercises `Find`/`At` on arbitrary bytes. Its `f.Add` seeds (canonical sample, OOM-repro claims, corrupt CRC, truncated prefixes) run as plain tests in CI. Real fuzz sessions use the command in Build & test. Add a seed for every new crafted-input bug you fix.

## validate <-> SPEC

`binpazer validate` implements SPEC.md's "Validation" section: the rule ids in `go/cmd/binpazer/validate_checks.go` (`allRules`) map one-to-one onto that checklist plus its implied checks (CRC trailers, footer/index consistency, structural parseability). If the checklist changes, update the rules and `validate_rules_test.go` (one corruption test per rule) together.

Decision to preserve: the `unknown_type_id` rule **exempts predefined ids 65529-65534** (SPEC.md notes the exemption). The writer emits the Block Index (65533) without a BTT entry and writer bytes are frozen. A strict reading will flag every indexed file. Teaching the writer to add the entry instead will change output bytes in all implementations plus the fixture.

## Appendable files (1.2)

SPEC.md "Appendable files" is the contract. Header flag the first bit marks the file, the CRC trailer of each block is its commit seal, and the End block (`65529`) closes it. Invariants to keep:

- **Committed means whole and sealed.** `NextCommitted` / `binpazer_reader_next_committed` / `Reader.nextCommitted` surface a block only when its full extent, padding included, is in the file and the CRC verifies. Pending and torn leave the reader at the block start with no sticky error, so the caller polls. Never surface a block on its length alone.
- **`TestFollowIsSafeAtEveryPrefix` (and `test_every_prefix` in C and C++, and "at every prefix a follower sees exactly the whole blocks" in `ts/src/append.test.ts`) is the safety proof**: at every length the file can have, a reader sees exactly the whole blocks. A change to the read path must keep it green.
- **Resume pads, it never overwrites in place.** A torn tail can hold a sealed block of its own (a child of a torn Group). So the resume writers -- `ResumeAppendWriter` / `binpazer_writer_resume` / `resumeAppendWriter` -- cover every stale byte with sealed Padding blocks before appending. The Padding layout is byte-identical across implementations and pinned by `go/testdata/sample-resumed.binpazer`.
- **The stays of the Block Type Table unsealed** in an appendable file. Readers in this repo older than 1.2 compute the table end without a CRC, so a sealed table breaks them.
- **An appendable writer keeps no index** (memory must not grow with the file), flushes after every block, and refuses `WriteIndex`. `Find` on an appendable file walks committed blocks only.
- Fixtures: `sample-appendable.binpazer` and `sample-resumed.binpazer`, from `gen <out> <compressed> <appendable> <resumed>`. The Go tests, `c/test_append.c` and `ts/src/append.test.ts` each compare their own writer against the files, so no CI step is involved.
- CLI: `follow` and `append` are the user surface, and the read commands walk through `walkNext`, which stops at the last committed block.

## Compression (1.1)

Block flag a later bit is `compressed`. The stored payload is a **Compression Envelope** (codec id + reserved + `uncompressed_length`, plus a 16-byte GUID for the `65535` escape), so codec identity lives in the format, not in a boolean. The earlier `compressed` flag was removed for exactly that reason. This is the codec-identifying mechanism SPEC.md said will replace it.

Invariants worth knowing before touching it:

- Go uses klauspost/compress and pierrec/lz4, C and C++ use zlib, libzstd and liblz4 through `c/binpazer_codec.c`. And TypeScript uses `node:zlib` for deflate and zstd plus its own LZ4 frame codec in `ts/src/lz4.ts`. No implementation may write a file another cannot read, so a codec added to one is added to every one or it is not added. `RegisterCodec`/`RegisterCodecGUID` (Go) and `binpazer_codec_register`/`_register_guid` (C) are for codecs OUTSIDE the registry (the GUID escape) or to override a built-in.
- **Parity means DECODE-compatibility, not same bytes.** A real codec's encoder output is implementation-defined -- zlib and klauspost/compress are under no obligation to agree, and do not. The byte-identity fixtures cover the uncompressed and `stored` cases, where agreement IS required. The interop check in the `go` CI job covers everything else. This has C write a file per codec. This holds for the Go CLI to decode and the Go CLI pack one per codec for `c/interop.c` to decode. Never "fix" a size difference between implementations -- it is not a defect.
- **The C core stays dependency-free. Codecs are a SECOND translation unit.** `binpazer.c` links nothing but libc and knows only the envelope (`binpazer_writer_block_compressed` takes bytes the caller already encoded). `binpazer_codec.c` adds the codecs and links `-lz -lzstd -llz4`. `make -C c test` builds both `test_c` (core alone, no codec library) and `test_codec`, so dependency-freedom is a CHECK, not a claim -- same split in C++ (`test_cpp` / `test_cpp_codec`). The codec entry points in `binpazer.hpp` are inline, so including the header never forces the link.
- **The caller-buffer API is the base layer everywhere**. The allocating forms are thin wrappers over it: `binpazer_compress`/`binpazer_decompress` and Go's `CompressInto`/`DecompressInto` write into a destination the caller owns and allocate nothing. Size it with `binpazer_compress_bound`/`CompressBound`. Which is why a bound is a required member of Go's `Codec` interface and a required function pointer in `binpazer_codec`. It must never under-report: too small a bound turns incompressible input into `ErrShortBuffer`, so `TestCompressBoundCoversIncompressibleInput` pins it against random data.
- `stored` (id 1) is the codec every implementation can run with nothing linked, which is why the cross-impl byte-identity fixture uses it.
- **`length` still counts STORED bytes**, so walking, skipping, `large_mode`, the Block Index and CRCs are untouched, and a 1.0 reader traverses a 1.1 file correctly. `has_crc` covers the stored bytes, before any codec runs.
- **A file with no compressed block is byte-identical to a 1.0 file** and still declares 1.0. Which is why a compressed block needs a seekable writer. Otherwise, an up-front declaration: Go's `NewWriterVersion`, C's `binpazer_writer_begin_version`, and the C++ `Writer` constructor's trailing `version_minor` argument all exist for streaming callers. Without one, a non-seekable writer refuses the block (`BINPAZER_ERR_NOSEEK`).
- `go/testdata/sample-compressed.binpazer` is the second cross-impl fixture, generated by `gen <out> <compressed-out>` and `cmp`'d in CI like the first.
- The CLI carries compression through `codec` in the pack/unpack manifest -- never a `compressed` flag name. So a manifest cannot claim compression without naming what produced the bytes. `unpack` writes DECODED payloads.
